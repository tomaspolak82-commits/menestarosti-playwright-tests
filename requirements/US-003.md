# US-003: Rychlost webu

| | |
|---|---|
| Stav | návrh k diskusi |
| Riziko (test-plan, část 3) | 2 – pomalý web |
| Oblast testů | `tests/performance/` |

## User story

Jako návštěvník chci, aby se web načetl rychle, abych nemusel čekat a nemyslel si, že nefunguje.

## Proč

Lidé nechtějí čekat a pomalý web považují za rozbitý. Rychlost je zároveň jeden ze signálů, podle kterých Google řadí výsledky vyhledávání.

## Akceptační kritéria

- **AK1:** Denně: skóre výkonu PageSpeed úvodní stránky na mobilu je alespoň na pevné spodní hranici.
- **AK2:** Denně: skóre úvodní stránky na mobilu neklesne výrazně pod průměr posledních 7 dní.
- **AK3:** Týdně: z každého měření (úvodní stránka, jeden článek, stránka s hrami; mobil i počítač) se uloží prostřední hodnota ze tří měření a porovná se s minulým týdnem. Výsledek je jen upozornění, test kvůli němu neselže.
- **AK4 (chybový stav):** Když PageSpeed neodpoví nebo vrátí chybu, výsledek se nevyhodnotí jako „web je pomalý“, ale jako chyba prostředí.
- **AK5 (chybový stav):** Když chybí klíč k PageSpeed, test hned selže se srozumitelnou hláškou, že klíč chybí.

Hranice pro AK1 a AK2 jsou v testovacích datech (`src/data/performance.json`).

## Sady

- Denní: AK1, AK2, AK4, AK5.
- Týdenní: AK3, AK4, AK5.

## Otevřené otázky

1. Hranice pro AK1 a „výrazně“ v AK2 doplníme po prvních měřeních. Návrh: spodní hranici nastavit kousek pod současné skóre, aby test hlídal zhoršení.
2. Hlídat kromě celkového skóre i jednotlivé ukazatele, které Google používá (rychlost zobrazení hlavního obsahu, poskakování stránky při načítání)? Navrhuji ano, protože celkové skóre může zůstat stejné, i když se jeden ukazatel výrazně zhorší.
3. Který článek měřit týdně? Navrhuji pevně jeden, nejčtenější, aby se dalo porovnávat v čase. Až budou statistiky, můžeme ho změnit.
